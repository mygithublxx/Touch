# 从想法到装进手机：这次 Touch 是怎么做出来的

写给没做过 App 的人。以这个项目为例子，把每一步做了什么、为什么这么做讲清楚。

---

## 一、先弄明白：一个 iOS App 到底是什么

你在手机上点开的每一个 App，本质上是一个**文件夹**，扩展名 `.app`。里面装的是：

| 内容 | 是什么 | 在 Touch 里 |
|---|---|---|
| 可执行文件 | 编译后的机器码 | `Touch`（十几 MB 的二进制） |
| 资源 | 图片、声音、界面描述 | `Assets.car`（App 图标）、`LaunchScreen.storyboard` |
| 配置文件 | `Info.plist`，声明名字、支持的方向等 | 自动生成 |
| 签名 | 一段密码学签名 | `_CodeSignature/` |

**关键点：iOS 只运行「签名有效」的 App。** 这是苹果的安全机制，也是为什么装到自己手机上还需要 Apple ID。

App 本身是「设备无关」的——同一份代码编译两次，分别得到「模拟器版」和「真机版」，两者的 CPU 架构不同。

## 二、整个流程：七个阶段

### 阶段 1：把想法变成明确的规则（最容易跳过、也最贵的一步）

你说的是「划一下就知道我选什么牌」，但真到写代码时，一堆问题没有答案：

- 一次滑动会穿过好几个格子，到底取哪个格子？→ 最后定成**起点格**
- 四个方向只有四个花色，但「往左上划」和「往正上划」怎么区分？→ 按四个象限归类
- K 那一行只有一张牌，横向划到哪儿都算 K 吗？→ 是，整行都算
- 划错了能不能重来？→ 能，短于 34pt 的滑动直接忽略
- 表演者自己看不见屏幕，怎么知道划对了？→ 你选了纯肌肉记忆，不做任何辅助

这一步的产出叫**需求 / 设计文档**，存放在
`docs/superpowers/specs/2026-10-28-touch-ios-design.md`。

> 经验：需求阶段每多花 10 分钟，后面少返工 1 小时。这个项目里「梅花和方块对调」
> 就是因为一开始把方向写反了，后来返工了一次。

### 阶段 2：选技术（由工程师决定，你不需要懂细节）

| 选择 | 结果 | 理由 |
|---|---|---|
| 语言 | Swift | iOS 官方语言，唯一现实选择 |
| 界面框架 | SwiftUI + 少量 UIKit | SwiftUI 写页面快；刮层/自绘需要 UIKit 的精确控制 |
| 遮挡检测 | 距离传感器 | 不用摄像头 → 无权限弹窗、无状态栏绿点 |
| 最低系统 | iOS 17 | 覆盖绝大多数在用手机 |

### 阶段 3：写代码

代码量其实很小，全部加起来约 1200 行：

```
Touch/
├── TouchApp.swift              10 行   程序入口
├── Models/Card.swift          125 行   一张牌是什么；屏幕坐标 → 牌
├── Flow/AppModel.swift        108 行   状态机（待机/选牌/锁定/解锁/出牌/翻牌）
├── System/ProximitySensor.swift 41 行  距离传感器
├── Views/
│   ├── Stages.swift           103 行   开始页、黑屏页、锁定页
│   ├── RootView.swift          75 行   根据状态决定显示哪一页
│   ├── CardViews.swift        264 行   牌面（点位排布）、牌背（鳞纹+徽记）
│   ├── FlipCardView.swift      61 行   3D 翻转动画
│   └── TutorialView.swift     283 行   教学页 + 屏幕分区图
└── Assets.xcassets/                    App 图标
```

真正「有难度」的只有三处：坐标换算、3D 翻转的透视、遮挡传感器的系统限制。其余是界面拼装。

### 阶段 4：构建（把代码变成 .app）

```
xcodebuild -project Touch.xcodeproj -scheme Touch build
```

这一步做三件事：编译 Swift → 打包资源 → 签名。产物在 `build/Build/Products/...`。

### 阶段 5：在模拟器里验证

模拟器就是电脑上跑的一个「虚拟 iPhone」，不用手机也能看到界面。
它的问题是**没有传感器**：距离传感器、真实相机、真实触感都没有。
所以「遮挡解锁」在模拟器里用「长按 1.6 秒」代替。

### 阶段 6：自动化测试（这次的关键投入）

人眼检查「点一下翻出来的牌对不对」很容易漏。所以我们写了 UI 测试，
让程序自己操作 App 并断言结果：

```
启动 → 点开始 → 在指定坐标划 → 模拟遮挡 → 断言出现牌背 → 点一下 → 断言牌面是「梅花6」
```

一共三条链路，分别验证三种花色方向。这就是为什么「梅花/方块对调」这种改动
我可以确信没改错，而不是靠眼睛看。

跑测试：`xcodebuild test`

### 阶段 7：装到真机

这是普通用户最容易卡住的一步，因为它涉及苹果的账号体系：

| 概念 | 通俗解释 |
|---|---|
| Apple ID | 你的苹果账号。开发者用的就是它，不用另外注册 |
| Personal Team | 免费账号对应的「个人开发团队」，能签 7 天有效的 App |
| 证书（Certificate） | 证明「这个 App 是这个人做的」 |
| 描述文件（Provisioning Profile） | 授权「哪些设备可以装这个 App」 |
| 设备 ID（UDID） | 每台 iPhone 的唯一编号，要登记进描述文件 |
| 开发者模式 | iOS 16 起的安全开关，不打开就不允许装开发版 App |

完整链路是：

```
Xcode 登录 Apple ID
  → 提出生成证书（Private Key 存进 Mac 钥匙串，所以会问一次 Mac 开机密码）
  → 第一次装真机时自动登记你的设备 ID
  → 苹果服务器签发描述文件
  → 用证书 + 描述文件给 App 签名
  → 通过 USB 把 .app 推进手机
  → 手机上「信任」这个开发者
```

`7 天有效期` 是免费账号的限制：描述文件到期后 App 就打不开了，要重新签一次。
付费开发者账号（¥688/年）是一年有效，还能用 TestFlight 无线分发。

## 三、这次实际踩过的坑（真实开发就是这样）

| 现象 | 原因 | 修法 |
|---|---|---|
| 牌翻过去后变成一条竖线贴在左边 | 3D 变换默认绕左上角旋转，牌被转出屏幕 | 先平移到中心再旋转，转完平移回去 |
| 刮层是灰的但底下的花纹透出来 | 混合模式 `copy` 把噪点画成了「半透明洞」 | 画完底色立刻切回 `normal` |
| 冷启动闪一下白屏 | 默认启动屏是白的 | 加一个纯黑的 `LaunchScreen` |
| App 图标没有出现 | 工程里没告诉 Xcode 用哪个图标 | 加 `ASSETCATALOG_COMPILER_APPICON_NAME` |
| 安装脚本报「手机未连接」 | 系统接口的「连接状态」字段滞后 | 不再依赖它，直接尝试安装 |
| 翻牌后测试断言失败 | 背面元素在无障碍树里仍然存在 | 给两面分别加 `accessibilityHidden` |

## 四、你以后想改东西，怎么改

| 你想改 | 改哪里 | 难度 |
|---|---|---|
| 花色方向对应关系 | `Models/Card.swift` 里 `switch` 的最后四行 | ★ |
| 网格行数/列数 | 同文件 `rows` / `columns` | ★★（要同步改教学页的图） |
| 最短滑动距离 | 同文件 `minimumTravel = 34` | ★ |
| 牌背花纹、颜色 | `Views/CardViews.swift` 的 `CardBackView` | ★★ |
| 牌面样式 | 同文件 `CardFaceView` | ★★ |
| 首页按钮、文案 | `Views/Stages.swift` | ★ |
| 教学页内容 | `Views/TutorialView.swift` | ★★ |
| App 图标 | 跑 `swift scripts/make-icon.swift 输出.png`，再替换图标文件 | ★★ |

改完统一走这两步：

```bash
xcodebuild test                          # 确认没改坏
./scripts/install-to-iphone.sh           # 重装到手机（插上线）
```

## 五、如果你想自己去 App Store 上架

和现在的差别只有三件事：

1. 注册**付费**开发者账号（¥688/年）
2. 在 App Store Connect 里创建 App 记录，填名字、截图、隐私说明
3. 上传构建版本 → 提交审核（苹果人工审，通常 1–3 天）

审核通过后，全世界都能在 App Store 搜到它。
但注意：**这个 App 的功能本质是「魔术道具」**，上架时描述要写成「纸牌预测 / 互动娱乐」，
不要写成「读心术」这类可能引起误解的表述。
